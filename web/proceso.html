Esta página documenta, en el orden real en que ocurrió, cómo se hizo este sitio y los seis modelos que consume: Naive Bayes Gaussiano, un Perceptrón Multicapa y dos Procesos Gaussianos, entrenados en Python y exportados a ONNX para correr aquí mismo, en tu navegador. Cada entrada corresponde a un capítulo del informe de desarrollo, con los comandos, las cifras y las decisiones tal como salieron — incluido lo que falló primero.

Las métricas que ves abajo no están escritas a mano: son las mismas que lee la pestaña Comparativo del simulador, leídas de models/registry.json.

01clonar

Clonar el repositorio y leer el plan de trabajo

El equipo partió de un repositorio con un único documento real: docs/PLAN_DE_TRABAJO.md, la guía de la actividad con 12 secciones (protocolo de evaluación, modelos asignados, exportación a ONNX, matriz de trazabilidad contra la rúbrica). Todo lo que sigue es ese plan ejecutado sección por sección, no una estructura inventada aparte.

$ git clone https://github.com/Calamar49/Comparativo-de-Familias.git $ cd Comparativo-de-Familias $ python -m venv .venv && .venv\Scripts\activate $ pip install -r requirements.txt && pip install -e .
02paquete

Un paquete Python instalable, no un notebook suelto

src/familia3/ se instaló con pip install -e . para que los notebooks, los tests y la web compartieran exactamente el mismo código de carga de datos, pipelines y métricas — nada duplicado ni copiado entre archivos.

Cada módulo hace una sola cosa; pipelines.py (Pipeline de scikit-learn con StandardScaler) es el que terminan consumiendo búsqueda, exportación y notebooks por igual.

desde_cero.py reimplementa Naive Bayes, MLP y Proceso Gaussiano en NumPy puro, sin scikit-learn, solo para verificar la matemática: gradientes comprobados por diferencias finitas, y una comparación numérica directa contra el modelo de scikit-learn con el mismo kernel fijo.

datos.py también construye el experimento de sensibilidad a atípicos (contaminar_outliers) que pide la sección 6 del plan: mismo dataset, una fracción de puntos corrompidos, mismo protocolo de evaluación.

04entrenar

Entrenar, exportar a ONNX y registrar con su hash

python -m familia3.todo es el único comando que entrena los seis modelos, los exporta, prueba que el .onnx responde igual que el modelo de Python, y escribe models/registry.json con versión, SHA-256 y métricas de cada uno. La web nunca lee un número escrito a mano: lee ese registro.

Si el hash descargado en el navegador no coincide con el del registro, el modelo se rechaza — lo comprueba verificar_release.py en cada ejecución de CI.

Lo que falló primero: skl2onnx no logra exportar un GaussianProcessRegressor con normalize_y=True y return_std=True a la vez (revienta dentro de un operador interno, OnnxMul). Con la normalización activada, gpr_diabetes daba R² = −3.91: el optimizador del kernel convergía a un mínimo degenerado donde el modelo solo predecía el promedio. La solución fue estandarizar el objetivo a mano antes de entrenar y guardar y_offset/y_scale en el registro — la web deshace esa transformación igual que lee cualquier otro dato del modelo. Con eso, R² subió a 0.510.
05notebooks

Cinco notebooks, cada uno con una pregunta distinta

Ejecutados de punta a punta con jupyter nbconvert --execute --inplace, sin celdas con error. No repiten el mismo análisis con otro dataset: cada uno responde algo que los anteriores no cubren.

  • 01Datos y protocolo: partición 80/20 estratificada, por qué el 20% de prueba no se toca hasta el final.
  • 02Naive Bayes Gaussiano: fronteras cuadráticas, búsqueda de var_smoothing, sensibilidad a atípicos.
  • 03MLP: curvas de aprendizaje, efecto del escalado, comparación de arquitecturas por RandomizedSearchCV.
  • 04Proceso Gaussiano: bandas de incertidumbre, NLPD, cobertura del intervalo, el hueco deliberado en los datos 1D.
  • 05Comparativo: prueba de McNemar entre NB y MLP sobre el mismo conjunto de prueba, aplicaciones prácticas de cada familia.
06sitio

Un sitio que consume los modelos, no que los simula

La web no reimplementa Naive Bayes ni el MLP en JavaScript: descarga el .onnx real, verifica su SHA-256 contra el registro y lo ejecuta con ONNX Runtime Web, enteramente en tu navegador. Cinco pestañas: Naive Bayes, MLP, Proceso Gaussiano, Comparativo y Teoría.

Se puede fijar una versión exacta con ?version=nb_cancer:v1 en la URL, para reproducir un resultado anterior del registro.

Un detalle que costó encontrar: al comparar Naive Bayes y MLP a la vez en la pestaña Comparativo, lanzar las dos inferencias con Promise.all rompía ONNX Runtime Web (TypeError dentro de su propio código). Dos sesiones distintas no se pueden correr en paralelo de forma segura con el backend wasm; la solución fue consultar una sesión a la vez, con await secuencial.

En la pestaña de Proceso Gaussiano, la banda de incertidumbre (media ± 2σ) se ensancha visiblemente justo en el hueco que sintetico_seno1d deja a propósito entre 3 y 5 — el modelo admite, de forma honesta, que ahí no vio datos.

07ci

Integración continua: que nadie rompa el registro sin darse cuenta

.github/workflows/ci.yml corre en cada push: instala dependencias, corre las 19 pruebas, reentrena y republica los seis modelos, y verifica que el registro siga siendo consistente antes de subir dist/ como artefacto descargable.

09netlify

Desplegar: arrastrar dist/ y listo

Sin paso de compilación: netlify.toml solo fija publish = "dist". El equipo generó dist/ localmente con python -m familia3.todo y la arrastró a un sitio nuevo de Netlify. El sitio quedó publicado en:

https://comparador-familias.netlify.app/

Ahí corren los mismos seis modelos, con la misma verificación de hash que en local — nada se procesa en un servidor.
